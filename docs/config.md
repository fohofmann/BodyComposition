# Configuration reference

`PipelineConfig` is the only supported configuration boundary. Defaults live
in package code, so the API, CLI, wheel, and container cannot select different
files based on the current directory. Configuration schema version is `1.0.0`.

Generate the complete resolved YAML and validate an override with:

```bash
bodycomposition config show-default -o bodycomposition.yaml
bodycomposition config validate bodycomposition.yaml --json
```

Python exposes the same behavior:

```python
from BodyComposition import PipelineConfig, configuration_schema

config = PipelineConfig.load("bodycomposition.yaml")
resolved = config.normalized()
json_schema = configuration_schema()
```

Unknown keys, wrong container types, unsupported backend IDs, and invalid
runtime values fail before models are loaded. An override is recursively
merged onto defaults, but it is not a compatibility layer for old pipeline
names.

## Minimal override

```yaml
schema_version: 1.0.0
models:
  root: /models
runtime:
  device: auto
  cpu_threads: 8
reporting:
  enabled: true
  layout: spine_profile_v2
```

The complete field list and defaults are generated by `config show-default`.
That generated file, rather than a hand-maintained copy in this document, is
the authoritative reference.

## Scientific choices

| Section | Purpose | Released choices |
| --- | --- | --- |
| `orientation` | anatomy-based integrity check and safe lossless repair | `ctdeeprot_2d_v1`, policy `check_and_safe_repair` |
| `vertebrae.backend` | vertebral-body segmentation and native labeling | `spineps_veridah_ct_v1`, `vertebral_bodies_resenc_l`, `vertebral_bodies_resenc_m` |
| `tissue.backend` | anatomical body-composition compartments | `bodycomposition_resenc_l_v1`, `bodycomposition_resenc_m_v1` |
| `body_surface.backend` | measurement support for trunk/body envelope | `tissue_segmentation_envelope_v1`, `totalsegmentator_body_task299_v1`, `deterministic_body_mask_v1` |
| `measurements` | tissue definitions, physical territory rules, landmarks, QC | canonical schema 2.1 |
| `reporting` | derived one-page PDF | disabled, `spine_overview_v1`, or `spine_profile_v2` |

No backend silently falls back to another. Changing a backend or a scientific
threshold changes the scientific configuration digest and `analysis_id`.

The default orientation model runs on CPU because its 2-D inference is small
relative to the segmentation stages. `orientation.model_device` may be set
explicitly. SPINEPS/VERIDAH and the overall runtime accept `auto`, `cpu`, or
`cuda`. `auto` selects an externally visible CUDA device and otherwise CPU.
Apple MPS is not a released scientific-inference target because the complete
pinned model stack has not passed a controlled MPS validation gate.

## Runtime and output choices

`runtime.cpu_threads` is an upper bound; zero uses the process CPU affinity.
`runtime.max_workers` is fixed to one. To use multiple GPUs or processes, start
the same batch command multiple times against the same shared output. Each
process claims whole cases and owns one externally assigned accelerator.

`runtime.timeout_seconds` limits a stage. `runtime.fail_fast=false` records a
failed case and continues unrelated cases. With fail-fast enabled, unstarted
cases receive explicit cancelled manifests.

`runtime.deterministic=true` enables deterministic PyTorch algorithms where
available. `runtime.allow_dirty=false` blocks cohort execution from an
uncommitted source tree. Set it only for clearly recorded development runs;
dirty runs cannot pass the release gate.

Output toggles control persisted derivatives, not scientific inference. The
run stores the queue-compatible configuration projection; each case manifest
stores the complete redacted configuration of the worker that produced it.
Reporting requires `output.save_tissue_labels=true` because the axial overlay
must remain reproducible from the immutable case bundle.

## Environment variables

Only operational paths and shared-worker controls use environment variables:

- `BODYCOMPOSITION_MODEL_ROOT` supplies the default `models.root`;
- `BODYCOMPOSITION_OUTPUT_ROOT` supplies the default result root (`./output`
  outside the container and `/output` in the released container);
- `BODYCOMPOSITION_HEARTBEAT_SECONDS`;
- `BODYCOMPOSITION_STALE_AFTER_SECONDS`;
- `BODYCOMPOSITION_MAX_CLAIM_SECONDS`;
- `BODYCOMPOSITION_MAX_ATTEMPTS`; and
- `BODYCOMPOSITION_POLL_SECONDS`.

Container build provenance may also provide `BODYCOMPOSITION_GIT_SHA`,
`BODYCOMPOSITION_SOURCE_SHA256`, and `BODYCOMPOSITION_SOURCE_DATE_EPOCH`.
Manifests record variable names or redacted provenance, never secret values.
There is no environment variable that changes to a newer model or enables an
inference-time download.

## Analysis identity

The case-level `configuration_sha256` covers the complete resolved worker
configuration. The run-level `configuration_sha256` covers the
queue-compatible projection used to decide which workers may share work. That
projection excludes device selection, CPU allocation, timeout, model-cache
path, vertebral runtime device, dirty-source permission, and logging level. It
retains scientific settings, output selection, reporting, determinism, and
fail-fast behavior.

`scientific_configuration_sha256` excludes model-cache location, reporting,
log/output toggles, CPU allocation, and device selection, but retains
determinism because it may affect numerical output.

`analysis_id` additionally covers input pixels and physical geometry, source
revision/tree digest, and verified model assets. A successful case resumes
only when that identity is identical. Patient position in a scanner or a local
file name is not used as an identity shortcut.

## Tissue sensitivity profiles

Repository examples in `config/tissue_profiles/` are strict partial overrides.
They make alternative published HU windows or preprocessing explicit and are
validated in tests. They do not define clinical phenotypes and do not alter
the raw prepared CT used for reported attenuation. See
[tissue definitions](tissue_definitions.md).

## Migration from pre-1.0

Remove the old `method`, named-pipeline YAML, global `config/config.yaml`, and
command-specific configuration. Generate a new default, then copy only the
scientific changes you intend to retain. Replace old pipeline names with the
corresponding explicit backend fields. There is intentionally no runtime
translation or deprecation shim.
